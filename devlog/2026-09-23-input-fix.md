# 2026-09-23 — Input fix: USB controller dead on v0.1

## Report

v0.1 ignored a USB game controller (no reaction to START or other
buttons) while the same setup played a commercial ROM (F-Zero) fine.
So the defect is in our pad path, not the emulator mapping.

## Root cause: stale auto-joypad reads

`read_pads` (hardware branch) spun only on auto-read *completion*:

```
while (REG_HVBJOY & 0x01u) { }
gj_pad = $4218/$4219...
```

But it runs immediately after `wait_vblank` exits at vblank START,
while the SNES auto-joypad read only *begins* a few hundred cycles
into vblank (~2 scanlines long). Arriving before it starts, bit 0
reads idle, the spin is skipped, and `$4218/$4219` return the
*previous* frame's (or power-on) latch. Combined with full-screen
redraw ticks that slip frame phase, sampling vs the auto-read window
goes erratic: stale/mid-read values, perceived as a dead controller.
Commercial games (F-Zero) use the SDK sequence: wait for busy-start
AND busy-end, guaranteeing a fresh sample every frame.

## Fix (src/main.c, hardware branch only)

```
while (!(REG_HVBJOY & 0x01u)) { }  /* wait for read to start */
while (REG_HVBJOY & 0x01u) { }     /* wait for it to finish */
```

Safe by construction: auto-joy is enabled once (`NMITIMEN=$81`) and
never disabled, and every vblank performs a read on hardware and both
test emulators. Self-drive (`script_pads`) is untouched, so the
capture-script tour and LLM testing path are unaffected.

## Companion changes (title screen)

- Title now accepts **A as well as START** (standard confirm; helps
  any pad/emulator combo where Start is awkwardly mapped).
- **Input debugger**: hold SELECT on the title to see live
  `$4218/$4219` bytes (`PAD lo hi`) on the prompt row. Readout is
  cleared on release. Lets a human verify bit delivery directly.
